# UI System spec — review from the commands & input angle

**Verdict: REQUEST CHANGES.**
1. The direction is right: one command table, one dispatch, pointer capture, logical px and an Escape ladder are the correct fixes for audit 04.
2. The spec is missing the one concept every desktop standard has: a **responder rule**. It does not say who gets ⌘C/⌘Z/⌘A while a text field is focused. As written, L11 would break copy/paste/undo inside fields on the Mac (P1-1).
3. L13 (Tab/⌃F6) contradicts S2 §3.7's Start keyboard contract, and egui 0.35 cannot implement it (P1-2). `EditSession` is too wide in one place and too narrow in another (P1-3).
4. The spec ignores what S1-D is already building (`host.rs`: queue, pointer capture, lifecycle keys before the text gate), so U1 duplicates it and opens a second dispatch home (P2-6).
5. Everything below is a small text change. With P1-1…3 applied, this angle approves.

Evidence: the spec at `6b37c2b`; audits 01/04; DFS S1 §3.5–3.6 and S1-D WIP `dbfe87b` (`.claude/worktrees/agent-a4de…/varos/crates/varos-app/src/host.rs`); S2 §3.7; S4–S6 §3.3; QW5 review; registry sources winit 0.30.13, egui 0.35.0, egui-winit 0.35.0, muda 0.20. I built nothing and ran nothing. Every claim is from reading the code.

## Findings

**P1-1 · No responder rule: L11 + L13 break text editing on the Mac and contradict each other.**
*Evidence:* winit's macOS view has no `performKeyEquivalent` (grep in `platform_impl/macos` = 0). So a muda accelerator (⌘C/X/V/A/Z) is taken by the menu, and the keyDown never reaches winit. Today the only way these keys reach a focused egui field is the menu row → `forward_shortcut` (`ui.rs:925-938`: `Event::Copy/Cut/Paste` plus a synthetic key for Z/A), which is exactly `MenuCmd::Key`. L11 deletes `MenuCmd::Key` and says "never through a synthetic keystroke". L13 says canvas shortcuts yield to a text field. Neither law says whether **Edit ▸ Undo with a field focused** undoes the field or the document; both laws claim that case. DOCUMENT_FILE_SYSTEM §4 wants both "dispatch once through command IDs" and "modal text inputs keep normal editing keys".
*Change:* add one column to `CommandSpec`, `scope: Scope { App, Text, Canvas }`, and replace L11/L13's focus clauses with:
> L11 "…never through a synthetic keystroke, and mirror each native row's enabled state from `resolve`." → "…through one `dispatch`. Responder rule: while `text_edit_focused`, a `Text`-scope command (Undo, Redo, Cut, Copy, Paste, Select All, Delete) goes to the field as its egui text event (`Event::Copy/Cut/Paste`, or the key for Z/A); a `Canvas`-scope command (plain letters, Space, arrows, Delete) yields; an `App`-scope command (File, View, Window, Object rows) always runs. This is the only place a key is handed to egui."
*Test:* field focused → Edit ▸ Copy puts the field text on the clipboard; Edit ▸ Undo undoes the field; File ▸ Save saves; V types "v".

**P1-2 · L13 contradicts S2 §3.7, and egui cannot do it as written.**
*Evidence:* S2 §3.7 says the Start page uses "Tab/Shift+Tab traverse actions and rows; Enter activates; Delete removes the focused recent row", and gives a focus outline on buttons. L13 allows Tab "only among fields of the focused box". egui 0.35's focus traversal is global: `memory/mod.rs:560-680` walks every `FOCUSABLE` widget in registration order and has no scope. So "fields of the focused box" and ⌃F6 box cycling each need a custom focus engine, and `Mods{primary,shift,alt}` cannot even express ⌃F6 on a Mac (see P2-5). B4's real cause is that `Sense::click()` = `CLICK | FOCUSABLE` (`sense.rs:60`), so Tab lands on a button, after which that button also eats Space/Enter.
*Change:* L13 → "Canvas shortcuts yield only while `text_edit_focused`. Kit buttons, rows and swatches are not focus stops (`Sense::CLICK` without `FOCUSABLE`) except on Start and in dialogs. Tab/⇧Tab is fed to egui only when a text field is focused, Start is shown or a dialog is open, so on the canvas Tab does nothing and between fields it moves to the next field." Move ⌃F6 and box focus to Risk 8's accessibility spike.
*Test:* Tab then V on the canvas selects the Selection tool; Tab on Start focuses New; Tab in W goes to H.

**P1-3 · `EditSession` is not minimal and not complete, and L4 contradicts §3.2's `settle`.**
*Evidence:* Only two UI edits hold core `pending` across frames: the picker and a scrub (audit 04-A1). `Drag` is the Editor's own gesture, which S1-A's `DocumentSession::settle` already finishes. `Rename` is a UI buffer with no `pending`. L4 says a rename "commits before any foreign Request". §3.2 says `settle` "discards rename buffers — as S1 defines". So ⌘S while renaming (or while typing "120" in W, which is in no session kind at all) saves the old value, and the tab turns dirty right after the save. `num_field`'s buffer lives in egui memory (§3.3 signature has no state), so the host could not commit it even if it wanted to.
*Change:* `SessionKind { Picker(PickerTarget), Scrub(FieldKey) }`, with Rename and Drag deleted. Add to L4: "A focused text edit (field or rename) is committed (if valid) before any App/Edit request runs, Save included; `settle` discards it only for Close/Quit → Don't Save." Give `num_field` an explicit `&mut FieldEdit` state (like `inline_edit`). Flag the S1 `settle` change to the moderator; it is additive.

**P2-4 · `route(event, …)` over winit events cannot be tested headlessly.** `winit::event::KeyEvent` has `pub(crate) platform_specific` (`event.rs:651`), and `InnerSizeWriter` is `pub(crate)` (`event.rs:980`), so a test cannot build a `KeyboardInput` or a `ScaleFactorChanged`. S1-D already works around this with pure fns over `KeyCode + Mods`.
*Change:* L18 → "`route(InputEvent, &InputState, &FocusSnap) -> Vec<Action>`, where `InputEvent` is our own enum (Key{code, pressed, repeat}, Button, Move, Wheel, Pinch, Focus) filled by a ≤ 40-line `from_winit` adapter." `FocusSnap` = `{ text_focused: ctx.text_edit_focused() (context.rs:2889), popup_open: ctx.any_popup_open() (context.rs:2910), modal, start_shown, canvas_gesture }`, read at the end of the previous frame. The Esc ladder and "a click outside a menu does not reach the canvas" (§4) both need `popup_open`, which `KeyCtx` omits.

**P2-5 · The key types add a 4th translation table and break L18.** `Chord { key: Key }` with "our enum; egui/winit/muda codes derived" means three match tables (today there are 2 plus Debug strings). muda is a macOS-only dependency (`Cargo.toml` `[target.'cfg(target_os = "macos")']`), so "muda adapters derived here" in `ui/commands.rs` needs a `cfg`, which L18 forbids. `Mods` cannot express physical Control on a Mac: DFS §4 wants Ctrl+Tab, and L13 wants ⌃F6.
*Change:* `Chord { code: winit::keyboard::KeyCode, mods: Mods { primary, ctrl, shift, alt } }`. Physical keys keep shortcuts working on an Arabic layout, and that should be written as the rule. `KeyCode → muda::Code` stays in `platform/mac_menu.rs`. The egui mapping shrinks to the Text-scope keys. Rule: "a chord without `primary` is never a native accelerator" (generalises QW5's Delete row). Add a table test: no two rows share (chord, scope); no row uses a macOS-reserved chord (⌘H ⌘M ⌘Q-except-Quit ⌘Tab ⌘Space ⌃↑ ⌃↓, 04-I4). Tab switching therefore cannot take ⇧⌘]/[, which is Bring to Front/Back (`chrome.rs` Arrange).

**P2-6 · Dispatch must build on S1-D's `host.rs`, not beside it.** S1-D (in flight) already has `host::{menu_route, key_command, run_lifecycle, route_left_release}`. It also has a `pending: Vec<AppCommand>` queue drained at `AboutToWait`, pointer capture for the left button (`LeftRelease::Chrome`), lifecycle keys before the text gate, and a `!event.repeat` guard. The spec invents `ui/dispatch.rs` and lists pointer capture as new U1-C work. There is also a real ordering bug in the S1-D shape: doc keys run inline (`doc_key`), while lifecycle commands queue. So ⌘S then ⌘Z in one event batch saves after the undo.
*Change:* §3.1 `ui/dispatch.rs` → "`host.rs` (S1-D) grows `dispatch(Request)`". Add to L11: "…one FIFO queue drained at one point, in the order raised." U1-C: drop pointer capture (done), and extend `route_left_release` to middle/right and to `CursorMoved` hover. Absorb `FileCmd`, `lifecycle_key`, `to_app_command` and `MenuCmd::{File, Plain, Toggle*, Snap*}` into `CommandId` rows (`MenuCmd` ≡ `CommandId` + `Native`). Amend DFS S4–S6 §3.3: S6-C adds `CommandId::FileExport` rather than `FileCmd::Export`, and its planned `MacMenu::sync_enabled(|FileCmd|)` becomes the one `sync_enabled(|CommandId|)`. S2-E2's Open Recent rows carry a `Request` directly. They are dynamic, argument-carrying rows outside the argument-free table, so say so in L10.

**P2-7 · Refusal belongs to dispatch, not only to the menu mirror, and "document commands" must be spelled out.** `resolve` must run for **every** source (key, native row, button, tab strip). The native-row mirror lags a frame, and AppKit may pass a disabled row's ⌘-key down as `KeyboardInput` (not verified in the window). A re-check at dispatch makes both harmless. L4's modal rule → "While a modal session is open, dispatch accepts only the session's own requests, `View(..)`, `App(..)` (which settle it first) and Text-scope commands to a focused field; everything else resolves to `Disabled("Close the colour picker first")`." Implementation hint: egui 0.35's `egui::Modal` (`containers/modal.rs`) with a transparent backdrop blocks panels, and it makes `wants_pointer` true over the canvas too. So no new canvas gate is needed, and there is no shadow.

**P2-8 · L15 conflates two scales.** In egui-winit, `pixels_per_point = zoom_factor × window.scale_factor()` (`lib.rs:50-54`). They are equal only while egui's zoom factor is 1 (the app disabled keyboard zoom, `ui.rs:1565`, but nothing pins it). egui-winit already updates its native ppp on `ScaleFactorChanged` (`lib.rs:311-323`), so the host needs no new arm.
*Change:* L15 "(one source: winit `ScaleFactorChanged` = egui `pixels_per_point`)" → "(canvas: `window.scale_factor()` read at use, never cached; chrome: egui `pixels_per_point`; a test pins `ctx.zoom_factor() == 1`)".

**P2-9 · U1 and U5 break the day cap and the dependency order.** U1-B's `resolve(id, &Snap) -> Result<Request, _>` needs `Snap` and `Request`, and U2-A creates both. U1-B also rewrites 31 `apply_key` arms + 17 `shortcut` arms (audit 04 sizes this "L"). U5-B is admitted "L". It needs core `cancel_gesture` in `editor.rs` (Esc restores `pending`), which the hot-file queue does not list, and `host.rs` is missing from the queue.
*Change:* U1-A also creates `ui/request.rs` and a 7-field `CmdCtx { has_doc, has_sel, can_undo, can_redo, session, text_focused, start_shown }` that U2-A later folds into `Snap`. Split U1-B into B1 (native rows: File/Edit/View/Object/Window → CommandId, `sync_enabled`) and B2 (tool/plain keys, delete `apply_key`/`shortcut`). Split U5-B into B1 (move-only `input/route.rs` with tests), B2 (Esc/Enter ladder + core cancel), B3 (reset, Space-pan, hover, double-click). Queue: `editor.rs` … → U5-A → U5-B2. Add a `host.rs` row: S1-D → U1-B1 → U1-B2 → S2-E2 → U5-B1.

**P2-10 · U5-C trackpad, verified against winit 0.30.13.** `WindowEvent::PinchGesture` exists on macOS (`view.rs:703-723`, `magnifyWithEvent:`). Its `delta` "may be NaN" (`event.rs:290`). `DoubleTapGesture` (smart zoom) and `RotationGesture` exist too. `TouchpadMagnify` is the old 0.29 name. egui-winit turns the pinch into `egui::Event::Zoom` and marks it consumed when egui wants the pointer (`lib.rs:513-521`). winit calls `mouse_motion` before queueing, so the cursor position is fresh. `PixelDelta` is already physical px (`view.rs:670`), so 1:1 pan is right.
*Change:* U5-C text: "`PinchGesture` (NaN/non-finite ignored, dropped over chrome) → `zoom *= 1 + delta` at the cursor; `PixelDelta` 1:1; ⌘/Ctrl+wheel = zoom at the cursor on every platform (Windows precision-touchpad pinch arrives as Ctrl+wheel)". Delete `Platform.pinch`, because the event simply never arrives elsewhere.

**P2-11 · L16 can reuse egui instead of a new helper.** egui already has `InputOptions { max_click_dist: 6.0, max_double_click_delay: 0.3 }` (`input_state/mod.rs:67-117`), which all egui widgets use. Set both once from `DRAG_THRESH` and `Platform.double_click_ms`. Keep the custom helper only for the canvas and the caption (not egui). The OS interval needs objc2-app-kit feature `"NSEvent"` (`NSEvent::doubleClickInterval`; a feature flag, not a new crate) and Windows `GetDoubleClickTime` (feature already on). This changes L16's test: "…the canvas and caption call the helper; egui's `InputOptions` equal the same values."

**P3-12 · L10: remove "and window title".** S1 dropped the tool name from the title (`host::window_title`). Add: hints order modifiers ⌃⌥⇧⌘ as AppKit renders muda accelerators; test `hint(FileSaveAs, mac) == "⇧⌘S"`. Once that holds, the macOS native menu stays the visible source of hints: its muda accelerators come from the same `Chord`, and there is no second table. Keep `every_menu_key_has_a_native_key_equivalent`, pointed at `TABLE`.
**P3-13 · Repeat policy in the table.** Add `repeats: bool` (nudge and zoom true, everything else false) instead of U5-B's ad-hoc `event.repeat` guard (04-B10; S1-D guards lifecycle keys only).
**P3-14 · L5 guards only in debug.** In release, `begin` still overwrites `pending` silently. Merge L5 into L4 and add: "dispatch never runs an `Edit` while `editor.transaction_open()` (S1-A) and no session owns it; it settles first."

## Whole-spec answers (this angle)
1. **Laws.** Merge L5 into L4. Rewrite L13 (P1-2). Sharpen L11 (P1-1, P2-6/7), L15 (P2-8), L16 (P2-11) and L18 (P2-4). L18's "no `cfg` in `ui/`" contradicts §3.1's muda adapter (P2-5). L14 stays but needs `popup_open`. L17 is partly done by S1-D (mods reset after every lifecycle command); keep it for focus loss and Space.
2. **Simplest?** No. Remove the `Key` enum, `ui/dispatch.rs` (use `host.rs`), Rename/Drag session kinds, ⌃F6, `Platform.pinch` and the custom double-click helper for egui surfaces. No new dependency is needed on this angle.
3. **Plan.** U1 depends on U2 types (fix: P2-9). U1-B and U5-B exceed the cap. The hot-file queue lacks `host.rs` and U5-B's `editor.rs` slot. S6-C and S2-E2 need work-order amendments (P2-6). U1-C is smaller than listed because S1-D already did pointer capture.
4. **Decisions.** Q1–Q5 are fair on this angle. The input choices hidden in "smaller items" (Tab, Enter, ⌥ step) are right. Add the items below.
5. **World-class reviewer.** An Apple reviewer would ask first for the responder chain and the command validation (enable/refuse at the point of dispatch), and then for chord collision and reserved-chord checks. Figma would add a stated keyboard-layout policy (physical keys, US legends in hints: say it, because Arabic is the moat). Blender would add the rule that the one table later feeds a command palette and user keymaps; name it as the extension point, and do not build it now.

## Needs Ahmed (recommended default)
1. **Tab on the canvas does nothing. Tab jumps between text boxes. Buttons are not Tab stops, except on the Start page and in dialogs.** Default: yes.
2. **⌘S while you are typing a number or a name: keep what you typed, then save.** Default: yes.
3. **Mac tab switching = ⌃Tab / ⌃⇧Tab only.** ⇧⌘] and ⇧⌘[ stay Bring to Front / Send to Back. Default: yes.
4. **Two-finger double-tap on the trackpad (Mac "smart zoom").** Default: do nothing in V1.
5. **Moving keyboard focus between boxes (⌃F6).** Default: later, together with accessibility.
