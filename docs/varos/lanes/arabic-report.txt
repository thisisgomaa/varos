Caret/selection
Source text stays unchanged; cluster offsets are valid, selection produces 25
quads and endpoint carets have the correct RTL order. Exact caret fidelity is
incomplete. The sample caret->hit roundtrip fails at (source byte, hit byte):
(9,7), (11,7), (13,15). Native caret code takes the first glyph covering a cluster;
virtual kashidas and ligature components share source ranges. Full selection
geometry/affinity and editing interaction were not verified.

Three real pain points
1. Font identity/metadata: Varos requires static family names and rejects TTCs.
   The bounded family table and external Noto fallback are spike-only; original
   font breaks/metrics can differ from fallback. An added fallback fixture first
   failed because Source Sans missing-glyph widths already wrapped into two lines;
   the final 1200pt fixture tests fallback identity without assuming new breaks.
2. Editing maps: overlapping clusters from virtual glyphs/ligatures disagree with
   the native one-glyph caret lookup, with the three measured mismatches above.
3. Composition integration: the adapter composes each already-selected line with
   a fresh Engine/FontSet and accepts only one-run/default-attribute RTL lines.
   Proper mixed-run shaping, shared font/shape caches and paragraph-wide kashida
   break/metric decisions require more than this additive hook. Absolute local
   dependency/font paths also need replacing for a portable implementation.

Effort for the proper version: L (font/instance registry and caches, mixed runs,
paragraph composition and exact editing maps, then runtime native/web/PDF QA).
