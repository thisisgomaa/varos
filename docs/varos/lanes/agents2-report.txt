Lane: lane-agents2 (Opus 5.5), 2026-10-26, base main f4b20c72. Not committed (the moderator lands it).
Issue: VQA-11 (P1, production test with ChatGPT-driven agents): agent commands followed "the active
document", so when the person switched tabs they hit the wrong document (object-reference
failures, an export written from an unintended document). Re-activating first only narrowed the
race.

WHAT CHANGED (IN ONE LINE)
Every agent operation now names its board (open document) by a stable id; the app resolves it by
id inside the single UI-thread turn that runs the request, never by "the tab in front", and gives
the person's tab back in the same turn.

THE RULES (what an agent sees)
- Board id: "<launch>-<uid>", e.g. "9f3a1c2e-3". uid = DocState::uid (process-unique, survives
  other tabs closing or moving; the tab index does not). launch = 8 random hex digits made once per
  launch, so an id from before a restart is refused (session_reset), never taken for a new
  document that happens to get the same uid.
- Revision: a per-board content revision (varos_agents::boards::Revisions). It moves when the art
  changes (anyone's edit, an undo to another state), not when the person selects, scrolls or saves
  (upstream's DocState::revision moves on selection too, so it would make every save stale).
- Object references: ids leave the MCP server as "<board>:<id>" and are turned back into plain ids
  on the way in. A reference of board A in a call naming board B is refused as wrong_board before
  anything is sent. References alone also name their board (a call with only references runs on
  their board; references of two boards in one call are wrong_board).
- Every MCP tool takes `board` and `revision` (schema properties added to all tools). Saves and
  exports (anything that writes a file from a board: save_file, export, command_run file.save /
  file.saveAs / document.export* / file.export.*, screenshot or render to a path, and such steps
  inside command.batch / action.batch) need board + revision.
- Through Varos' agents port, while any board is open, every request that reads or changes a
  document must name its board (board_required). Exempt: the lists (engine.commands, ui.inspect,
  menus/tool lists, varos.boards), tool/panel/window settings (ui.tool.select, ui.set, ui.resize,
  ui.focus), and making or opening a board (file.new, file.newBoard, file.open, document.open,
  file.newFromTemplate, app.open). With no board open (Home) nothing can be misrouted, so nothing
  is required.
- Every reply that ran for an agent carries varos: {board, revision, front, opened}: where it ran,
  that board's revision now (use it next), the board in front (the person's), and boards the
  request opened or made.

ERROR CODES (prefix of the error text, "<code>: why. Nothing was run.")
- board_required: no board named where one must be, or a save/export without its revision, or a
  tab index given instead of a board (file.close {index}).
- board_not_found: the board is not open (closed, or not an id).
- session_reset: the id is from an earlier launch of Varos; call list_boards again.
- target_changed: (a) a verb that acts on the window (see FRONT-ONLY) names a board that is not the
  one in front (the person switched tabs); (b) document.activate from an agent (agents never switch
  the person's tab); (c) after the run: the request left its board for another existing board, or
  opened a dialog on a board lent the front (the dialog is dismissed).
- stale_revision: the board changed since the revision given.
- wrong_board: an object reference of another board.
- person_busy: the person is dragging, typing or composing (IME) on their board; lending another
  board the front now would end that gesture (upstream's tab switch finishes the tool's work).
  Retry in a moment.

HOW THE APP RUNS A REQUEST THAT NAMES A BOARD (ui-egui varos/boards.rs, in drain_control)
All of this happens inside the one UI-thread turn that handles the request; the person's clicks are
processed in frames, so no tab switch can come between these steps.
1. enter: resolve the id (session_reset / board_not_found), check the revision when given and
   require it for writes (stale_revision / board_required), refuse window verbs on a board not in
   front (target_changed), refuse while the person's tool is working (person_busy), then lend the
   board the front with Session::varos_lend_front (sets the active index without
   reset_tool_for_doc_switch, so the person's tool state is not finished or cancelled) and verify
   the active uid is the target.
2. The existing agents::before (actor, write guard, presence) and control::handle run, now on the
   target (so the write guard's "own file" is the target's file, presence is drawn on the target).
3. leave: verify the request ended on its board (or a board it opened, or it closed its board) and
   that it opened no dialog on a lent board; then give the person's board the front back (also
   after an agent's file.new/open: a new board opens behind the person's; when the person was on
   Home it stays in front); attach varos {...} to the reply.
Upstream's `--control` port is unchanged unless a line names a board (then the same steps run,
without the board_required rule and the tab restore for unlent requests).

WINDOW VERBS (item 5: where restoring is impossible, and why) -- revised in round 2, see below
- Agents (Varos' agents port) may not drive the person's window at all: ui.click, ui.drag, ui.key,
  ui.text, ui.move, ui.wheel, ui.pointer, ui.tool.select, ui.set, ui.resize, ui.focus,
  ui.dialog.set / confirm / cancel and app.quit are refused as person_state (synthetic input is
  consumed by later frames, after the turn; it drives the person's own tool and selection).
- ui.screenshot (window capture) runs only when its board is in front, else target_changed; a
  capture admitted for a board is refused, with no file, when another board is in front by the
  time it is taken or written (upstream's document identity check, tested for agents).
- Clients of upstream's --control port that name a board keep synthetic input, front-only, and
  input still queued when the board leaves the front is dropped at injection (varos.dropped).
- ui.menu.invoke is the same handler as engine.execute and is treated as one.

MCP SURFACE (`vectorcraft-cli mcp`, crates/mcp)
- New tools: capabilities (call first: api "varos-boards/1", the rule, error codes with what to do,
  the front-only and board-free tool lists) and list_boards (board, title, path, dirty, revision,
  front, artboards; plus top-level front).
- All tools: `board` and `revision` properties; save_file, export and screenshot descriptions say
  revision is required; front-only tools say their board must be in front.
- initialize instructions (Backend::describe of VarosAttach) state the rule.
- Mapping to the verb names in the brief (they are the pre-fork varos-bridge's): describe/snapshot
  = doc_inspect / render_preview; edit = command_run / command_batch / draw_* / set_paint / ...;
  select = command_run select.*; save / save_as = save_file / command_run file.saveAs; export_pdf =
  export {format: pdf}; list_boards and capabilities are new here.
- resources/read: a board's resources are vectorcraft://board/<board>/<resource> (document,
  document/json, object/<id or <board>:<id>>, swatch/<name>, effect/<id>), read on that board only,
  ids qualified; vectorcraft://commands and command/<id> need no board; the old board-less form of
  a board's resource is refused (board_required, with the new URI). Completions carry no board (the
  app answers board_required for a board's data while one is open).
- Upstream backends: --headless refuses a `board` (it has no boards); --connect forwards it.

WHAT IS LEFT / RISKS
- Object references are made from key names (id, ids, created, parent, path, selection, objects,
  selected) in tool results. An object id under another key in some command's result stays a
  plain number (it is then taken on the board the call names). vectorcraft://object/{id} resource
  URIs take plain ids only.
- The "verify again" step reports a request that ended on another existing board as
  target_changed but does not roll that back (its steps are in that board's History, tagged with
  the agent). Known ways to do that (document.activate, file.close {index}) are refused up front.
- No tab reorder exists in this app yet; id stability is tested across tabs closing (indices
  shift, ids don't).
- The installed /Applications/Varos.app (2026-10-10) is the pre-fork build with its own
  varos-bridge, and ~/.claude.json's `varos` MCP server points at it. If VQA-11 ran against that
  bridge, this lane does not change it; the fix lives in the fork's `vectorcraft-cli mcp` + app.
- Not hand-tested in the real window (no GUI here; agents never take over the Mac).

ROUND 2: CODEX REVIEW FIXES (2026-10-27, on top of the merge of main 9e96e863 + docs)
1. Batches escaped their target. Now: for agents, a batch step that closes, opens, makes or switches
   a board (file.close, file.closeAll, document.close, document.activate, file.new, file.newBoard,
   file.open, document.open, file.newFromTemplate, app.quit) is refused before anything runs
   (target_changed); file.closeAll and app.quit are refused for agents outright (person_state).
   For any request naming a board the engine is pinned to it (Session::varos_pin; check in
   Session::execute before every command, each batch step included): a step that would run on
   another board fails with target_changed, the rest don't run, and the failed batch rolls back.
2. Synthetic input lost its board after admission. Now: agents may not send synthetic input at all
   (person_state). For --control clients naming a board, every queued run of synthetic events is
   tagged with its board, and raw_input_hook drops a run whose board is no longer in front before
   injecting anything (screen_synthetic); the next reply carries varos.dropped with target_changed.
3. Deferred captures: upstream's pipeline (from the merge) records the document identity (uid +
   revision) at admission and fails the capture before issuing and before writing when it differs;
   agents' captures are front-only and need board + revision. Tested: a capture admitted for A with
   the person on B by issue time answers "the document changed" and writes no file.
4. The person's tool, selection and view. Now: tool, view, window, workspace and ui command
   families, ui.tool.select and ui.set are refused for agents (person_state). For every agent
   request on a board, the person's selection, current layer, highlighted rows, isolation and that
   board's view are put aside and restored in the same turn; the agent gets its own selection and
   current layer per board (kept between its requests), so verbs that use "the selection" act on
   the agent's. A tool switch made by a request is undone.
5. Dialogs. Now: commands that are a dialog (edit.keyboardShortcuts, edit.preferences,
   file.documentSetup, file.newDialog, type.findFont) are refused for agents before they run, and
   those that open one when given no options (document.exportForOffice, file.export.pdf,
   file.export.svg, file.exportAs, file.exportForScreens, file.print, file.saveForWeb,
   object.slice.divide) are refused without options (needs_dialog). The person's open dialog is put
   aside while an agent request runs and given back untouched; any dialog a request still opens is
   dismissed and answered needs_dialog. A test runs every command the UI handles with no options
   and fails if one opens a dialog without being refused.
6. Writes in batches. Now: a batch (command.batch / action.batch) that saves or exports is refused
   for agents (write_in_batch); saves and exports are calls of their own, checked against the
   revision the batch answered.
7. Resources inherited the last tool's board. Now: board URIs (see MCP SURFACE), no fallback to a
   previously named board in the proxy.
8. Multi-call tools reused their first revision. Now: VarosAttach carries the revision each step's
   reply answered (same board only) into the tool's next step, so a tool's own edit doesn't make its
   later steps stale, while anyone else's edit between steps still does.
Also: the race test now consumes the queue through raw_input_hook instead of clearing it.
New error codes: person_state, needs_dialog, write_in_batch (in capabilities).
