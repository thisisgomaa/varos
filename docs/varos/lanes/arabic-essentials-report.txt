WHAT THE USER SEES
A. Middle Eastern options on by default
   - Preferences > Type > Show Indic Options is turned on once for every install, fresh or
     upgraded. Upgraded installs would otherwise keep their saved "off". After that the user's own
     choice stands; it is remembered in UiState.varos_middle_eastern.
   - Paragraph panel, under the alignment buttons: "Direction [Auto | RTL | LTR]".
     - The Auto segment names what it resolved to: "Auto (RTL)" / "Auto (LTR)".
     - It replaces upstream's two direction icon buttons, so the setting has one home.
   - Character panel, at the bottom: "Digits [Default / Arabic / Hindi / Farsi]" dropdown. The
     panel menu item still mirrors it.
B. Harakat colour (the headline item)
   - Character panel row "Harakat": four swatches (red, green, gold, black), Hide, As Letters.
   - It acts on the Type tool's selection or the selected type.
   - Hide = no fill: the marks stay in the text, for copy, search and export.
   - As Letters gives each harakat its letter's fill again.
   - Each click is one undo step.
   - Letters keep their joining and marks keep their place, bit for bit.
   - Kashida still stretches words whose harakat are coloured.
C. New type whose first letter is Arabic gets 150 % Auto Leading. This covers type made with
   text, and empty new type that the user then types Arabic into. Existing type and Latin type
   keep 120 %.
D. Glyphs panel > Show: Arabic Letters, Arabic Supplement, Arabic Extended-A, Arabic Presentation
   Forms-A, Arabic Presentation Forms-B. Forms-B is FE70-FEFC, without the byte order mark.
E. Verification
   - RTL Arabic on a path is correct: same glyphs, same visual order, Auto aligned to the path
     end, reversed and closed paths keep the glyphs.
   - PDF copy-back: Arabic letters and Hindi-drawn digits read back exactly as typed.
   - KNOWN ISSUE: a word set with a multi-letter ligature glyph (the Allah ligature) reads back
     reversed: "هللا" for "الله". Cause not established (export text map or importer). Not S, so
     not fixed. Recorded as an ignored test.
     Note: the round-trip was checked with our own PDF importer, not external viewers.

HOW B WORKS (upstream edit in crates/text/src/shape.rs, marked // Varos)
- Before: a run boundary inside a cluster split the shaping. So a harakat coloured apart from its
  letter was shaped apart from it, and the mark lost its attachment.
- Now: a boundary between runs that differ only in paint (fill, stroke and how it is drawn,
  overprint, style name) where a harakat sits on either side is no longer a shaping boundary.
- When such a boundary exists in a segment, the same segment is shaped once more with HarfRust's
  Characters cluster level. If that gives the same glyph sequence, each glyph takes the run of its
  own character; a ligature or composed mark takes its first character's run.
- Glyphs, clusters and positions are unchanged. Renderers, SVG and PDF already read the glyph's
  run, so they need no change.
- Latin accents keep upstream's rule (Arabic marks only).
- Kashida accepts words whose runs differ only in paint.

LEFT OUT / RISKS
- The Direction row shows the first paragraph's setting. It does not show a mixed state.
- The harakat swatches show no current state.
- Only four fixed colours. A custom colour is available through the command (`fill: "#RRGGBB"`)
  but not in the UI yet.
- Arabic leading heuristic: "empty type that receives Arabic". An old empty type object that the
  user types Arabic into also gets 150 %.
- If the character-level reshape ever yields different glyphs, colouring falls back to the
  letter's run for that segment. Glyphs never change; only the colour does not apply. This never
  happened in the 18 installed fonts.
- PDF: the Allah-ligature reversal (above). Copy-back from external PDF viewers is not verified.
- Translations are mine (23 languages); a native-speaker review is welcome.
