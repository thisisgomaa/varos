IMPLEMENTATION
No app per-panel profiler or puffin backend is configured. egui/eframe contain
profiling crate scopes, but the app has no configured collector for them; the
existing perf.frame_ms only measures the whole app UI pass.
Change A (diagnostics): opt-in native VAROS_PROFILE=1 section timers, reporting
at most once a second, top ten by total inclusive CPU time; mean, max and call
count. Timings are wall-clock durations of CPU-side sections and include any
scheduler preemption, not isolated per-thread CPU accounting. Sections overlap:
do not add ui.total + canvas + canvas.raster, or dock + its panel. Disabled scopes do not read a clock, allocate, touch egui state,
or request repaint. stderr failure is ignored intentionally. No dependencies.
WASM hooks are inactive. Individual dock/floating panel ids are timed, plus the
major chrome sections, canvas input/raster, font fallback and native menu sync.
The host logic and shortcuts are separate from the existing status-bar UI time.

The ignored headless benchmark exercises app.logic + app.ui in egui Context::run_ui,
using a fake native-menu backend (no AppKit). Each case uses 20 warmup frames,
waits for UI fallback fonts, applies them over two more frames, then measures
200 frames at 1440x900 logical pixels. Cases include still/moving
empty documents, a selected rectangle, and moving cases at pixels-per-point 2.
It also times shortcut-table construction separately. It excludes tessellation,
GPU upload/compositing, drawable acquisition, WindowServer, and input-to-photon
latency. The pointer regression checks that two new positions reach hover_doc in
the same frame and do not edit the document.

Change B (performance, separate from diagnostics): varos/shortcuts.rs adds a
pressed-key gate at the two command-shortcut table call sites. egui consumes
only pressed Key events (repeats included) from input.events. With none left,
all of the old command-chord checks would be false. The surrounding handler
still runs, including clipboard, text/IME, Escape bookkeeping and tool routing.
Key frames call the ORIGINAL builder, without caching, preserving ordering,
parameters and current overrides. No tool actions or command enablement changed.
Fixed call sites: shortcuts.rs:352 and :514; builder at :66. Default lookups
reach crates/engine/src/cmd/mod.rs:304 (a linear search). The builder did this
for every command even on pointer-only frames; its measured wall cost justified this fix.
This work happens in host.logic, OUTSIDE the existing status-bar UI timer.
Expected effect: less main-thread work on pointer/idle/text-only frames and
less pressure on refresh deadlines when CPU-bound. Input-to-photon improvement
still needs a window test; a vsync-bound case may show no latency change. This
does not by itself reduce the UI pass's displayed milliseconds.

A second runner, evidence/tests_headless.rs, links against the normal dev library's
public API and avoids waiting for test-only dependency builds. It runs one
case per process: at least 20 frames and 1.2s warming, then at least 200 samples
and 2.2s sampling (20,000 frame safety cap). It records full-frame p50/p95/mean
and the existing status UI mean. Its section breakdowns come from the opt-in
one-second profiler. Unlike the unit benchmark it cannot explicitly wait on
private fallback-font state; its warmup and process start are shown in raw logs.
Both runners set max_texture_side=8192 explicitly, matching a realistic native
texture allowance. Initial Retina runs used headless egui's 2048 default,
triggered caught internal errors and were REJECTED, not used as measurements.
The public runner now fails on an internal UI error; the unit runner asserts it.
The final profiler also flushes only AFTER the outer UI scope has closed, to
avoid splitting active parent/child section totals between reporting intervals.

FRAME FLOW (line numbers are in the final working tree unless noted)
- lib.rs:1433..1477 times the entire ui_frame, including canvas::show. Thus the
  status bar's 'ui 8.7 ms' is not a separate pure-egui cost to add to render 3.8.
  canvas.rs:394 chooses synchronous rendering below the previous-render >8ms
  threshold (also requiring same document and an existing texture for async).
  canvas.rs:399..403 performs rasterization and CPU-side texture preparation
  inside ui_frame in the synchronous case. Conversely render_ms is the latest
  render duration and remains displayed on frames that reuse the texture; it
  must not simply be subtracted from every UI sample.
- canvas.rs:233..237 handles current input before reading document state,
  rendering and painting overlays. canvas.rs:696..701 uses THIS pass's pointer
  hover position; canvas.rs:918..922 delivers motion to the tool before paint.
  No extra application pointer-event queue was found on the native input path.
  Automation's synthetic input queue intentionally spans frames (lib.rs input
  hook); it is not the native mouse path.
- canvas.rs:948..949 already requests immediate repaint on motion, a drag, or a
  modifier change. canvas.rs:692 does so during wheel glide. Adding another
  request on pointer motion would duplicate existing behavior.
- canvas.rs:323..324's 30ms request is ONLY placed-document bitmap polling.
  It is not a general 30ms frame/pointer throttle. render_worker.rs:59 wakes
  egui immediately after sending a finished render. No worker polling timer
  needs shortening.
- canvas.rs:333..340 uploads completed renders. canvas.rs:394..396 may submit a
  new job and canvas.rs:407..436 draws the previous same-document texture,
  reprojected for the current view. Current overlays are painted later in the
  same pass. On heavy documents the artwork can therefore be older than the
  overlay/UI by one OR MORE frames, depending on render completion. That is
  intentional asynchronous artwork latency, not an unconditional N/N+1 pair.
- lib.rs:1440..1457 draws control/status/dock chrome BEFORE canvas input. Those
  readouts can show the previous tool/selection state; in particular chrome.rs:734
  reads hover_doc before the canvas updates it. The status timings themselves
  are necessarily from an earlier completed pass. A forced second egui pass
  might refresh chrome, but adds CPU work; changing frame order or tool input
  routing is beyond a small measured fix here.
- macOS software cursor path: cursors.rs:575 disables OS bitmap cursors there;
  canvas.rs:585..593 paints the glyph through an egui tooltip-layer painter.
  It therefore waits for the current window frame's CPU work and presentation,
  whereas a hardware/OS cursor can move independently. This is display latency,
  not evidence that hover_pos contains the previous event. That path belongs to
  the cursor lane: cursors.rs was read only and was not changed.
- egui 0.36.2 context.rs:478..505 hit-tests CURRENT pointer input against previous
  PASS widget rectangles/layers. This can affect hover after layout changes;
  it does not delay the pointer coordinates on a stable canvas. Multiple
  layout passes can occur within one presented frame.
- egui-winit 0.36.2 lib.rs:352..355 requests repaint for CursorMoved. eframe
  0.36.2 epi_integration.rs:288..301 runs logic and UI in Context::run_ui, then
  wgpu_integration.rs paints that output. No extra egui frame queue was found.

Pinned Cargo.lock: egui/eframe/egui-wgpu 0.36.2, wgpu/wgpu-hal 30.0.1.
Cached dependency source was inspected read-only:
- egui-wgpu/src/lib.rs:87..95: AutoVsync and desired_maximum_frame_latency=1
  on macOS (the iOS exception does not apply).
- egui-wgpu/src/winit.rs:132..133 copies the requested latency into the actual
  SurfaceConfiguration before configure(). There IS a live-resize exception at
  :111..114: on macOS with macos-window-resize-jitter-fix it temporarily requests
  latency >=2 (three drawables) while resizing, then returns to the configured
  value. That feature is enabled in the normal app's resolved egui-wgpu build.
  This is window live resize, not ordinary canvas pointer motion.
- wgpu-core/src/device/surface_config.rs:66..68: AutoVsync tries FifoRelaxed,
  then Fifo. Metal adapter.rs:463..467 offers Fifo/Immediate, so this is Fifo.
- wgpu-core/src/device/resource.rs:5305 clamps the requested latency to caps.
  Metal adapter.rs:450..462 permits 1..=2 on supported macOS versions.
- wgpu-hal/src/metal/surface.rs:330 sets maximumDrawableCount to latency+1:
  normal requested latency 1 means TWO drawables, not one drawable. :337 enables
  display sync for Fifo. This configuration is not ignored on modern macOS.
- egui-wgpu/src/winit.rs:595..598 acquires the surface texture during painting,
  after app UI has run; :767 presents it. Acquisition/presentation/compositor
  waiting is not included in the app's 'ui' diagnostic. No actual Metal
  display, compositor queue depth, or scan-out latency was measured here.
Changing to Immediate risks tearing and needs an owner's window A/B test.
There is no supported evidence for changing the existing latency-1 setting.

WHAT FOUGHT THIS RUN
The initial offline build/test could not resolve cached icu_segmenter v2.3.0;
no online Cargo invocation or dependency edit was used. The cache populated
while the moderator/prebuild work continued. The first required app build then
passed after 2356.335s (39m16s), including the existing build-directory lock wait.
The UI tests have a separate, initially cold dependency graph and serialize
other Cargo commands behind that build lock. System load reached over 150 on
10 logical cores. No other processes or targets were killed or deleted.
The initial headless Retina configuration used a 2048 texture limit; those
caught-error runs are preserved as rejected-2048-limit-* evidence and excluded.
